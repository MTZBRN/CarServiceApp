## Root cause and reproduction

The data/upload directories and their files belong to UID/GID 1654, underneath
a root-owned 0700 ancestor. Docker bind mounts expose those directories directly
to the container, so its UID 1654 can read them. The host reader inherits directory
descriptors before its irreversible credential drop. Ordinary reads through
`/proc/self/fd/<fd>/app.db` work, as does upload traversal. However, SQLite's Unix
VFS resolves symbolic links when constructing its full database pathname. The
proc-FD link resolves back through the inaccessible host ancestor; SQLite fails
with `SQLITE_CANTOPEN` on the first migration-history connection. This happens
before database integrity, upload inventory, or logical-digest checks run.

This is a pathname-resolution defect, not a missing inherited descriptor, bad
SQLite URI encoding, Docker ownership transition, or corrupt WAL. The original
child caught the exception and exited 1, discarding the distinction.
See SQLite's [Unix VFS source](https://github.com/sqlite/sqlite/blob/version-3.45.1/src/os_unix.c)
(`appendOnePathElement` / `unixFullPathname`).

Local reproduction used a disposable QEMU Ubuntu 24.04 VM, Python 3.12.3 and
SQLite 3.45.1. The unmodified candidate failed the new private-ancestor test.
A separate descriptor probe passed ordinary DB/upload reads after dropping to
1654, then failed only SQLite open with `SQLITE_CANTOPEN`; the anchored-root
variant passed. No permission changes to the private ancestor were needed.

The Docker-backed reproduction also passed on that VM with Docker **28.0.4**,
a private **vfs** daemon with the workflow's bridge/iptables/forwarding restrictions,
and the same public Python fixture digest as the failed runner:
`sha256:935c3c5b12357a7e10caa9c1e6ca5692344d97cf229832ef584be2cec9fc03df`.
A network-disabled container with the same UID/GID and two bind mounts read the
fictional SQLite/uploads successfully. After its exit, the original candidate
failed and the corrected candidate passed against those exact files. The exact
container and private daemon were then stopped/removed. This local reproduction
does not substitute for the pending complete GitHub-hosted lifecycle run.

## Correction and unchanged safeguards

Only Gate D's owner-reader changes. In its root child, `fchdir(data_fd)` and
`chroot('.')` anchor SQLite's `/app.db` to the already-open validated directory.
The child then clears supplementary groups and irreversibly sets GID/UID before
reading any application content. SQLite continues using `mode=ro`, normal
locking and the real WAL/SHM alongside the same database inode. No immutable-mode
shortcut, DB-only copy, root SQLite read, host chmod, or mount is introduced.

Uploads are read as the owner relative to their separately pinned descriptor.
The child runs the existing fail-closed tree walk in that owner context and
compares the complete file-name set with the pinned helper's inventory. This
prevents the helper's default `os.walk` behavior from silently omitting an
unreadable directory. The helper bytes remain unchanged. The nonroot unit-test
path retains proc-FD access; operational CLI execution still requires root.

`sqlite3.dump` is imported before chroot because Python's `iterdump()` otherwise
tries to import it lazily from outside the child's root. Parent credentials,
working directory and root are unchanged. Child exit always closes its FDs.

Child failures now use fixed exit-code stages mapped by the parent to
`owner-reader-{namespace,credentials,uploads,migration-history,database-integrity,logical-digest,report}-failed`.
Signals and unrecognized exits report `owner-reader-signal-failed` and
`owner-reader-process-failed`. No exception message, path, environment, SQLite
row or inventory is printed. Existing report-size/time bounds remain in place.

Gate C bytes and tests, stopped-source integrity/custody checks, approval gates,
exact container/network/image identity, storage paths and recovery barriers are
unchanged by this correction. No deployment workflow or application code changes.
