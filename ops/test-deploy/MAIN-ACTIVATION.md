# Automatic TEST deployment from main

A push to protected `main` runs Workshop CI. After that run succeeds, the
dispatcher verifies the originating workflow, event, repository and full SHA
through GitHub’s API. It checks that SHA against the protected tip before the
`isolated-test` job and again before SSH. The secret-bearing job has no
checkout, cache, or CI artifact inputs.

The dispatcher keeps the existing `TEST_DEPLOY_ENABLED` repository variable
and the host keeps its root-owned `actions-enabled` marker. Deployments share
the existing GitHub concurrency group and server lock. The server refuses
replays of a revision with a healthy journal. Keep those journals as deployment
records and resolve any `in-progress` state through the existing recovery
procedure before requesting another run.

## Activation prerequisites

1. Keep both activation gates closed during Gate C/D execution. Complete the
   separately approved TEST cutover and acceptance, verify recovery readiness
   and run the installed preflight. Gate D acceptance authenticates the
   previously reviewed helper bytes, so leave that helper installed through
   acceptance.
2. With the gates still closed, review and stage this PR’s root-owned
   `scripts/test_deploy.py` and `ops/test-deploy/ssh-gate` at the existing
   `/usr/local/sbin/carservice-test-deploy` and
   `/usr/local/sbin/carservice-test-ssh-gate` destinations. They derive from
   the reviewed post-cutover implementation at `e1afb2e`. Retain its
   preflight, storage helper, reviewed frozen Compose, native baseline,
   environment and backup paths. Verify installed bytes, run the installed
   preflight against accepted TEST, and verify refusal with the gates closed.
   Preserve the existing forced command, key restrictions and exact sudo rule
   for `carservice-test-ci`. The updated forced command accepts only
   `deploy-test main <40 lowercase hex>` and sends only the SHA to sudo.
3. Require protection on `main` and restrict the existing `isolated-test`
   environment to the selected branch `main`. Keep the credentials scoped to
   that environment. Required environment reviewers pause every release, so
   any change to that TEST setting requires an explicit one-time authorization
   for unattended deployment. Until that decision, keep both gates closed.
   Preserve the reviewed protections for changes to `main` and its workflows.
   Verify
   `TEST_SSH_HOST` and the environment-scoped `TEST_DEPLOY_KEY` and
   `TEST_KNOWN_HOSTS` against the restricted account and independently
   verified host key. The fixed GitHub mirror must be able to fetch
   `refs/heads/main`, and the server’s separate read-only Actions credential
   must be able to verify Workshop CI.
4. Review the first current, CI-green `main` tip and explicitly authorize
   standing TEST deployment under the policy below. Once the recovery and
   environment checks are complete, open the server marker and set
   `TEST_DEPLOY_ENABLED` to `true` under that authorization. If the first
   successful CI run completed with the gates closed, rerun **Workshop CI**
   for that original push while it is still the tip.

## Standing TEST policy

The operator creates `/etc/carservice-test-deploy/continuous-policy.json` as
root-owned mode `0600`. A legacy `approved.json` cannot authorize this route.
The new file has no release SHA and is never generated by CI. Set these fields
from the reviewed, accepted TEST baseline:

| Field | Required value |
| --- | --- |
| `mode`, `branch`, `storage_layout` | `continuous-test-v1`, `main`, `test-root-v1` |
| `compose_sha256` | SHA-256 of the native baseline Compose JSON |
| `frozen_compose_sha256` | SHA-256 of the installed frozen Compose |
| `env_sha256` | SHA-256 of the installed private TEST environment |
| `migrations` | Complete ordered EF migration IDs already applied to accepted TEST |
| `migrations_tree` | Git tree ID of `Backend/CarServiceShop/CarServiceShop/Migrations` at the reviewed tip |

Obtain the tree ID in the reviewed repository with
`git rev-parse --verify <reviewed-tip>:Backend/CarServiceShop/CarServiceShop/Migrations`.
The policy admits successive protected `main` tips with successful exact-SHA
push CI while the pinned configuration and migration sources match. Keep EF
migration sources in the pinned directory. The release code still relies on
review of application startup behavior on protected `main`. The server
requires the full approved migration history before and after backend startup.
Migration or configuration changes require a separate reviewed operator
procedure and refreshed standing policy after the new baseline is accepted.
Close either gate to suspend automatic TEST deployment. PROD promotion remains
manual.

The server independently refetches the fixed `main` ref and checks exact tip
equality, branch protection, commit type, activation, standing policy and successful push CI
before building and again before stopping TEST. Coordinate branch changes
during the short deployment window after the final server-side tip check.
