## End-to-end traces

1. **Customer/repair:** staff form → typed request DTO validation (`B/Requests/WriteRequests.cs`) → controller → EF SQLite transaction plus minimal audit → protected API projection → session-bound React cache → staff display/print. Customer ID links vehicles; vehicle ID links appointments/jobs; job ID links parts. A list endpoint can reveal more fields than the visible screen uses.
2. **Authentication:** login text/password → bounded rate-limited BCrypt verification → user plus session row and audit → signed token → browser localStorage → bearer header → signature/lifetime and live database checks on every authenticated call. Passwords are not returned; account lists project safe fields. Revocation state can be rolled back by restoring an old database.
3. **Image:** multipart stream → raster decode/dimension check → re-encoded PNG/generated basename → filesystem → filename in account/audit action → publicly reachable static route. Replacement attempts to remove old owned file. Public URL access does not depend on current session state.
4. **Print/PDF:** protected worksheet/vehicle/settings reads → editable local preview → browser print subsystem. No backend PDF authentication endpoint exists to test; protection relies on access to source data, then endpoint/device controls. Downloaded/paper copies have a separate lifecycle.
5. **Backup:** stopped writers → full SQLite backup and uploads inventory/archive → permission-restricted plaintext artifacts/checksums → isolated restore → integrity validation. Real off-host custody, host snapshots and production recovery are outside verified scope.
6. **Deletion:** admin API guard + relationship checks → audited DB delete → optional best-effort owned image deletion. Historical audit, backups, SQLite remnants and external copies can remain. This is deliberate business CRUD, not a comprehensive subject-rights decision.

## Minimization and operational boundaries

Free-text notes/descriptions/part names/print fields can accidentally contain health, payment, identity-document or unrelated household information; no special-category workflow is designed. Staff guidance and field purpose limits should precede collecting any such material. Ordinary profile photos are not evidence of biometric processing. No customer photo/document uploader, OCR, payment-card storage, automated decision system, mail-sending integration or invoicing-provider API was found in the inspected baseline; these are not claims about manual workshop processes.

Potential recipients outside the code include the hosting provider, backup operator, printer/support personnel, invoicing service and customers receiving worksheets. Validate contracts, regions, subprocessors and actual manual transfers with the controller. The draft notice's statements are leads, not verified deployment evidence. No production/customer data is needed to settle the technical acceptance tests.

For each inventory row, the controller should record: purpose, lawful basis, accountable owner, necessity of fields, allowed roles, recipients/processors/locations, retention trigger and period, hold/exception rules, correction/export/restriction process and backup disposition. Keep this inventory current when Phase 6D/6E merges or a new document/OCR/notification integration is introduced.
